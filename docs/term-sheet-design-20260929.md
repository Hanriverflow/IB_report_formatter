# 텀싯(Term Sheet) 프로필 설계

> 작성일: 2026-09-29. 상태: 설계(구현 전). 범위는 1단계 `term-sheet` 프로필과 2단계 조건 변수·불일치 검사다. 상환스케줄 자동 계산 등은 후속 설계로 미룬다(§10). 이 문서는 요구사항과 설계이며 검증 기록이 아니다.

## 1. 목표

국내 DCM·구조화금융 텀싯(ABCP, ABSTB, ABL 등)을 Markdown과 YAML로 작성한다. 엔진은 이를 기관 양식을 갖춘, 편집 가능한 Word 문서로 만든다. 소유자가 꼽은 문제는 두 가지다.

1. **서식 맞추기.** 표 음영과 병합, 글꼴, 면책 문구, 고객확인란을 버전마다 손으로 맞춘다.
2. **수치 일관성.** 금액, 금리, 만기가 바뀌면 문서 여러 곳의 같은 숫자를 빠짐없이 고쳐야 한다. 수정은 원본을 고쳐 다시 생성하는 방식과 Word에서 직접 고치는 방식이 섞여 일어난다.

### 성공 기준

- 가상 샘플이 `--strict`로 생성된다. Word 페이지 검사에서 §5의 구성(기밀 표시, 첫머리 블록, 음영 라벨 표, 셀 병합, 주석, 고객확인란, 바닥글)이 모두 확인된다.
- 조건 표의 첫 세로선이 문서 전체에서 같은 위치에 정렬된다.
- `{{키}}`가 값으로 치환된다. 정의되지 않은 키는 strict 모드가 저장 전에 거부한다.
- 생성된 문서의 한 곳을 Word에서 고치면 `docx-audit`가 그 키의 불일치와 생성 후 변경을 보고한다.
- 기존 프로필의 출력은 바뀌지 않는다. `terms:`와 병합 기호가 없는 문서는 DocumentModel이 이전과 같다.

## 2. 범위

| 구분 | 내용 |
|---|---|
| 1단계 | `term-sheet` 프로필: 페이지와 글꼴, 첫머리 블록, 조건 표(라벨 음영, 셀 병합, 고정 라벨 폭), 셀 안 목록 기호, 주석, 고객확인란, 머리글·바닥글, 기관 문구 파일(house) |
| 2단계 | 조건 변수 `terms:`와 `{{키}}`, 값 태그(Word 콘텐츠 컨트롤), 생성 시점 스냅숏, `docx-audit` 조건 검사 |
| 후속 | 상환스케줄 자동 생성, Word 안 자동 연동, 구조도 전용 도식, DRAFT 워터마크(로드맵 E8), 컴플라이언스 표시(D3) |
| 범위 밖 | 조항 초안 작성(LLM이나 사람이 Markdown으로 쓰고 엔진은 변환만 한다), Word→Markdown 역변환(제품 경계상 금지) |

두 단계는 서로 독립적이므로 별도 PR로 낸다. 셀 병합과 조건 변수는 텀싯 밖에서도 쓸 수 있게 만든다. 다만 기존 프로필에서는 명시적으로 켤 때만 동작한다.

## 3. 공개 저장소 보호

저장소는 public이다. 다음 원칙을 지킨다.

- 실제 딜 문서는 샘플, 테스트 fixture, 문서 예시로 쓰지 않는다. 참고 양식은 gitignore 대상인 로컬 `tmp/`에만 둔다.
- 기관명, 기관 고유의 면책·고객확인 문구, 계좌번호, 당사자 이름은 저장소 밖 house 파일이나 로컬 문서에만 둔다. `.gitignore`에 `private/`를 추가해 저장소 안에 두는 실수도 막는다.
- 저장소의 샘플과 테스트에는 가상 이름(예: 가나다머티리얼즈㈜, 가나다제일차(유), 라마바은행)과 가상 계좌번호(`000-0000-0000-000`)만 쓴다. 가상 house 문구는 새로 쓴다.
- 이 설계서를 포함한 모든 문서에 실제 거래명과 당사자명을 쓰지 않는다.

### 4.2 frontmatter 키

| 키 | 필수 | 설명 |
|---|---|---|
| `profile` | 예 | `term-sheet` |
| `title` | 예 | 딜 이름. 첫머리 제목과 문서 속성 제목에 쓴다 |
| `subtitle` | 아니요 | 기본값 `Term Sheet` |
| `date` | 아니요 | 쓴 그대로 표시한다(예: `2026. 09.`) |
| `prepared_by` | 예* | 작성 기관·부서. house에 있으면 생략할 수 있다. `issuer`는 ABCP 발행 SPC와 혼동되므로 쓰지 않는다 |
| `disclaimer` | 예* | 면책 문구. house에 있으면 생략할 수 있다 |
| `confidential_label` | 아니요 | 기본값 `Strictly Confidential` |
| `confirmation` | 아니요 | 고객확인란 문구(§4.3 형식) |
| `version` | 아니요 | 바닥글 왼쪽에 표시한다(예: `v11`) |
| `house` | 아니요 | 기관 문구 파일 경로(Markdown 파일 기준 상대 경로 또는 절대 경로). CLI `--house`가 우선한다 |
| `terms` | 아니요 | 조건 변수(§6) |
| `tables` | 아니요 | 기존 표 사양에 `label_columns`, `spans`를 더한다 |
| `theme` | 아니요 | 기존 테마. 색과 글꼴을 바꾼다 |

`*` 표시한 `prepared_by`와 `disclaimer`는 frontmatter나 house 중 한 곳에 반드시 있어야 한다. 면책 문구 없는 텀싯은 내보내지 않는다. 같은 키가 양쪽에 있으면 frontmatter 값이 우선한다.

### 4.3 house 파일

기관마다 고정인 문구를 담는 YAML이다. 테마 YAML과 같은 원칙으로 알 수 없는 키는 거부한다. 허용 키는 `prepared_by`, `disclaimer`, `confidential_label`, `confirmation` 네 개다.

```yaml
prepared_by: "라마바은행 자본시장부"
confidential_label: "Strictly Confidential"
disclaimer: |
  본 자료는 논의를 위한 예비 조건이며 당행의 여신 제공 확약이 아닙니다.
  최종 조건은 내부 승인과 계약서에 따릅니다.
confirmation:
  intro: "아래 해당 항목에 표시하고 ( ) 안을 자필로 기재하여 주시기 바랍니다."
  items:
    - "□ 본인은 본 Term Sheet의 주요 조건과 위험에 대하여 설명을 들었습니다. (          )"
  signature: "고객확인 : 20    .    .    .   (서명/인)"
```

위 문구는 가상 예시다. 저장소에는 `samples/profiles/term-sheet-house.yaml`로 가상 문구만 둔다. 실제 문구는 저장소 밖 경로에 두고 `house:`나 `--house`로 지정한다.

### 4.4 본문 규칙

- 장 제목은 `## 1. 본건 개요`처럼 번호를 직접 쓴다. `## 별첨 | 상환스케줄(안)`처럼 번호 없는 장도 같은 `##`를 쓴다. 자동 번호는 붙이지 않는다.
- 소제목은 `###`를 쓴다.
- 셀 안 줄바꿈은 기존대로 `<br>`를 쓴다. 각 줄은 셀 안의 별도 문단이 된다(§5.4).
- `※`로 시작하는 문단은 주석 서식을 받는다(§5.5).
- 구조도는 이미지(`![구조도](structure.png)`)로 넣는다.
- 고객확인란은 빈 ```` ```confirmation ```` 펜스를 둔 자리에 house나 frontmatter의 `confirmation` 문구로 그린다. 펜스가 없으면 넣지 않는다. 이 펜스는 `term-sheet` 프로필에서만 인식하고, 다른 프로필에서는 기존대로 코드 블록이다.

### 4.5 셀 병합

- 셀 내용이 정확히 `^^`이면 바로 위 칸과, `<<`이면 바로 왼쪽 칸과 합친다. 앞뒤 공백은 무시한다. `^^`는 Markdown 표 확장(markdown-it-multimd-table)에서 쓰는 행 병합 기호를 따랐다.
- 합친 영역은 직사각형이어야 한다. 머리행과 본문 행은 서로 합칠 수 없다.
- 첫 본문 행의 `^^`, 첫 열의 `<<`, 직사각형이 아닌 영역은 오류로 본다. 경고를 내고 기호를 글자 그대로 두며, strict 모드는 저장 전에 거부한다.
- `\^^`, `\<<`는 글자 그대로 나온다.
- `term-sheet` 프로필에서는 기본으로 켜진다. 다른 프로필은 표 사양 `spans: true`일 때만 켜진다.
- 빈 칸은 어떤 프로필에서도 병합으로 해석하지 않는다. 빈 칸 보존 원칙은 그대로다.

### 4.6 라벨 열

- 라벨 열 수는 머리행 첫 칸이 덮는 열 수다. `| 구 분 | << | 내 용 |`이면 2, `| 구 분 | 내 용 |`이면 1이다.
- 표 사양 `label_columns`로 바꿀 수 있다. 값은 0 이상, 열 수 미만의 정수다. 0이면 라벨 음영을 넣지 않는다.

## 5. 출력 서식

참고 양식의 구성을 따르고, IB 문서 관행에 맞게 정렬과 쪽 나눔을 보강한다. 아래 색과 크기는 스타일 값으로 두어 테마로 바꿀 수 있다.

### 5.1 페이지와 글꼴

- A4 세로. 여백은 위 18mm, 아래 16mm, 좌우 15mm이며 본문 폭은 180mm다.
- 맑은 고딕을 라틴 문자와 한글에 함께 쓴다. 본문 9pt, 줄 간격 1.05.
- 한국어 어절 단위 줄바꿈(`w:wordWrap=1`)과 금칙 처리(`w:kinsoku`)를 켜고, 한글과 영문·숫자 사이 자동 간격(`w:autoSpaceDE`/`autoSpaceDN`)을 끈다. 새 프로필에만 적용하므로 기존 프로필 출력은 바뀌지 않는다. (2026-09-29 정정: 처음에는 `wordWrap=0`으로 적었으나, Word 실측 결과 `0`이 오히려 음절 단위 줄바꿈이었다. 계획 §2 참고.)
- 기본 강조색은 남색 `1A2270`이다. 테마의 `primary_color`로 바꿀 수 있다.
- 문서 속성의 제목은 `title`, 주제는 `subtitle`로 설정한다.

### 5.2 머리글과 첫머리 블록

- **머리글(모든 쪽):** 기밀 표시를 오른쪽에 7.5pt 기울임, 회색 `888888`로 넣는다. 참고 양식은 첫 쪽에만 기밀 표시가 있다. 쪽이 따로 전달될 때를 대비해 모든 쪽에 둔다. `confidential_label`을 빈 문자열로 주면 머리글을 비운다.
- **첫머리 블록(첫 쪽 본문 맨 위):**
  1. 제목: 가운데, 20pt 굵게, 강조색
  2. 부제(`Term Sheet`): 가운데, 16pt 굵게
  3. 날짜와 작성 기관: 가운데, 10pt, 각 한 줄
  4. 면책 문구: 양쪽 정렬, 7pt, 회색 `555555`, 위아래에 얇은 선
- 본문의 첫 H1이 제목과 같으면 한 번만 쓴다(기존 규칙 재사용). 표지, 목차, 문서 끝 면책 페이지는 없다.

### 5.3 조건 표

- 표 폭은 본문 폭(180mm) 전체다.
- **머리행:** 음영 `DCE3F5`, 굵게, 강조색, 가운데 정렬. 쪽이 넘어가면 반복한다.
- **라벨 열:** 음영 `F2F5FC`, 굵게, 검정, 가로·세로 가운데 정렬.
- **내용 열:** 흰 바탕, 왼쪽 정렬, 세로 가운데 정렬.
- **테두리:** 0.5pt `9AA5C4`. 셀 여백은 위아래 3.5pt, 좌우 5pt.
- **고정 라벨 폭:** 라벨 열이 1개나 2개이고 열 수가 "라벨 열 수 + 1"인 표를 조건 표로 본다. 조건 표는 라벨 첫 열을 33.5mm, 둘째 열을 30mm로 고정하고 나머지를 내용 열에 준다. 그러면 문서 안 모든 조건 표의 첫 세로선이 같은 자리에 온다. 그 밖의 격자형 표(여신조건, 상환스케줄 등)는 기존의 내용 기반 폭 추정을 쓰고, 머리행과 라벨 열 음영만 똑같이 적용한다.
- 숫자 열의 정렬과 표기 보존은 기존 표 사양의 `columns` 역할을 그대로 쓴다. 금융 의미는 추론하지 않는다.
- **단위 표기:** 표 사양의 `unit`은 표 위 오른쪽에 8pt 회색 `(단위 : 억원)` 형식으로 넣는다. `source`와 `as_of`는 기존 방식을 따른다.

### 5.4 셀과 본문의 목록 기호

셀의 각 줄은 별도 문단이 되고, 줄 앞 기호에 따라 내어쓰기를 한다. 그래서 줄바꿈된 둘째 줄이 기호 뒤 첫 글자에 맞춰 정렬된다.

| 줄 앞 기호 | 용도 | 왼쪽 들여쓰기 / 내어쓰기 |
|---|---|---|
| `•` | 1수준 | 0 / 3mm |
| `-` | 2수준 | 3mm / 3mm |
| `·` | 3수준 | 6mm / 3mm |
| `①`–`⑳` | 번호 | 0 / 4.5mm |
| `※` | 주석(8pt) | 0 / 4mm |

- 본문 문단도 `①`–`⑳`나 `※`로 시작하면 같은 내어쓰기를 받는다. 본문의 `-` 목록은 Markdown 목록이므로 기존대로 네이티브 번호로 렌더된다.
- 이 규칙은 기호를 보고 문단 서식만 정한다. 글자는 바꾸지 않는다.

### 5.5 주석, 고객확인란, 바닥글

- **주석:** `※` 문단은 8pt이며 §5.4의 내어쓰기를 받는다.
- **고객확인란:** 1열 표로 그린다. 안내문, 체크 항목, 서명 줄 순서이고 테두리는 0.5pt다. 한 쪽 안에 모이도록 행 분할을 막고 앞 문단과 붙인다.
- **바닥글:** 7.5pt 회색. 왼쪽에는 `version`이 있을 때 `Term Sheet v11`처럼 부제와 버전을 쓰고, 없으면 비운다. 오른쪽에는 `1 / 5` 형식의 쪽 번호를 쓴다.

### 5.6 쪽 나눔

- 장 제목, 소제목, 단위 표기는 다음 요소와 같은 쪽에 둔다.
- 표 행은 예상 줄 수가 12줄 이하이면 쪼개지 않는다. 그보다 긴 행은 쪼개질 수 있다. 모든 행을 분할 금지로 두면 긴 조항 행 앞에 큰 빈칸이 생기기 때문이다. 예상 줄 수는 기존 폭 추정과 같은 방식(열 폭당 글자 수)으로 계산한다.
- 표 뒤 간격은 본문 크기 빈 문단 대신 4pt로 줄인다.

## 6. 수치 일관성

### 6.1 조건 변수

- `terms:`는 키→문자열 매핑이다. 키는 `^[a-z][a-z0-9_]{0,39}$` 형식이다.
- 값은 문자열만 받는다. YAML 숫자 `1.10`은 읽는 순간 `1.1`이 되어 표기가 달라지므로 거부하고, 따옴표로 감싸라고 안내한다.
- 본문의 `{{키}}`를 값으로 바꾼다. 중괄호 안쪽 공백은 허용한다. 값은 Markdown으로 다시 해석하지 않고 글자 그대로 넣는다. 둘레의 굵게와 기울임은 이어받는다.
- **적용 위치:** 제목, 부제, 날짜, 장 제목, 문단, 목록, 표 셀, 인용 상자. 코드 블록, 인라인 코드, 링크 주소, 차트·도식 펜스에는 적용하지 않는다.
- `\{{`는 글자 그대로 `{{`로 나온다.
- `terms:`가 없는 문서는 치환하지 않는다. 기존 문서에 `{{`가 글자로 들어 있어도 출력은 바뀌지 않는다.
- 정의되지 않은 키는 경고를 내고 `{{키}}`를 그대로 둔다. strict 모드는 거부한다.
- 한 번도 쓰이지 않은 키는 로그로만 알린다. 경고 목록에 넣지 않으므로 strict 거부 대상이 아니다.

### 6.2 값 태그와 스냅숏

- 치환된 값마다 Word의 일반 텍스트 콘텐츠 컨트롤로 감싼다. 태그는 `ibrep:term:<키>`, 제목(alias)은 `<키>`다. 잠그지 않으므로 Word에서 그대로 고칠 수 있다. 평소에는 일반 글자처럼 보이고, 클릭하면 테두리가 나타난다.
- 생성 시점의 값을 문서 사용자 지정 속성 `ibrep.term.<키>`에 기록한다. 기존 생성기 서명 속성과 같은 장치를 쓴다. 태그가 하나 이상 달린 키만 기록한다.
- 외부 송부용 깨끗한 사본이 필요하면 `layout: {term_tags: false}`나 CLI `--no-term-tags`를 쓴다. 이때는 컨트롤과 스냅숏 없이 값만 넣는다.
- 링크 표시 글자 안의 조건은 치환하되 태그는 달지 않는다.

### 6.3 Word 편집 후 검사

`docx-audit`는 조건 태그가 있는 문서를 검사하면 JSON에 `terms` 항목을 추가한다.

| 결과 | 의미 | 수준 |
|---|---|---|
| `mismatched` | 같은 키의 값들이 서로 다르다(한 곳만 고친 경우) | warning |
| `changed` | 생성 시점 스냅숏과 달라진 키와 현재 값. 원본 YAML에 되돌려 반영할 목록이다 | 정보 |
| `missing` | 스냅숏에는 있는데 그 키의 컨트롤이 문서에서 모두 사라졌다(덮어쓰기, 삭제) | warning |
| `indicative` | 값에 `[ ]`가 남아 있는 키. 확정 전 조건 목록이다 | 정보 |

- 변경 추적이 켜진 문서는 삭제 표시를 뺀 현재 글자로 비교한다.
- 구조 오류(`issues`)는 늘리지 않는다. 따라서 종료 코드와 strict 렌더 검증은 바뀌지 않는다.
- 이 검사는 태그된 값끼리의 일관성만 본다. 태그 밖에 손으로 쓴 숫자나 조건의 재무적 타당성은 판단하지 않는다.

| `term_sheet.py`(신규) | house 로딩과 검증, 첫머리 블록, 고객확인란, 셀 목록 기호 서식, 머리글·바닥글 |
| `ib_renderer.py` | 표 병합 적용, 텀싯 표 스타일 분기, 조건 run의 콘텐츠 컨트롤 감싸기, `render()`에서 텀싯 첫머리와 머리글·바닥글 호출 |

| `md_to_word.py` | `--house`, `--no-term-tags` |
| 문서 | README·README.ko의 프로필 표와 작성 규칙, CHANGELOG, 가상 샘플과 house 파일, `.gitignore`의 `private/` |

- 새 조립 경로는 만들지 않는다. 공문 프로필이 `office_layout.py`를 쓰듯, 텀싯도 `IBDocumentRenderer.render()` 안의 프로필 분기에서 `term_sheet.py` 함수를 호출한다. `ib_renderer.py`가 이미 3,500줄을 넘으므로 텀싯 전용 코드는 새 모듈에 둔다.
- 기존 `termsheet` 프리셋(표지, 목차, 면책을 끄는 구성 묶음)은 호환을 위해 그대로 둔다. README에 `term-sheet` 프로필과 다르다는 점을 적는다.
- **위험:** python-docx의 `Paragraph.text`와 `Paragraph.runs`는 콘텐츠 컨트롤 안의 글자를 보지 않는다. 그래서 렌더러 후처리와 검사 도구는 글자를 XML(`w:t`)이나 DocumentModel에서 읽어야 한다. 테스트로 이 경로를 고정한다.

## 8. 오류 처리

| 상황 | 일반 모드 | strict 모드 |
|---|---|---|
| 정의되지 않은 조건 키 | 경고, `{{키}}` 원문 유지 | 저장 전 거부 |
| 문자열이 아닌 조건 값, 형식에 맞지 않는 키 이름 | 오류로 변환 중단 | 오류로 변환 중단 |
| 잘못된 병합 기호 | 경고, 기호 원문 유지 | 저장 전 거부 |
| house 파일 없음, YAML 오류, 알 수 없는 키 | 오류로 변환 중단 | 오류로 변환 중단 |
| `prepared_by` 또는 `disclaimer` 없음 | 오류로 변환 중단 | 오류로 변환 중단 |
| `confirmation` 펜스가 있는데 문구가 없거나 펜스 안에 내용이 있음 | 경고, 펜스 원문을 코드 상자로 보존 | 저장 전 거부 |

## 9. 테스트와 검증

- **파서:**
  - 병합: 정상, 첫 행 `^^`, 첫 열 `<<`, 직사각형이 아닌 영역, 이스케이프, 다른 프로필에서 무시, `spans: true`
  - 라벨 열 계산
  - 조건 치환: 굵게 안, 코드 안, 이스케이프, 정의되지 않은 키, 숫자 값 거부, `terms:` 없는 문서의 무변경
- **렌더러(생성 XML 확인):**
  - 셀 병합(`w:vMerge`, `w:gridSpan`), 음영과 테두리 색, 모든 조건 표에서 같은 라벨 폭
  - 셀의 줄별 문단과 내어쓰기
  - 콘텐츠 컨트롤 태그와 사용자 지정 속성
  - 머리글·첫머리 블록 순서, 고객확인란, 바닥글, `w:wordWrap`
- **검사 도구:** 가상 문서를 생성한 뒤 XML을 고쳐 Word 편집을 흉내 낸다. `mismatched`, `changed`, `missing`, `indicative`가 보고되는지 확인한다.
- **회귀:** 기존 테스트가 모두 통과하고, 기존 샘플의 DocumentModel과 출력이 바뀌지 않는다.
- **샘플:** `samples/profiles/term-sheet.md`와 가상 house 파일을 추가해 기존 샘플 일괄 테스트에 포함시킨다.
- **페이지 검사:**
  - 기존 `scripts/word_visual_qa.ps1`로 새 빈 폴더에 가상 샘플의 페이지 이미지를 만들고 모든 쪽을 확인한다.
  - 로컬 참고 양식과 구성·정렬을 눈으로 비교한다. 참고 양식과 그 이미지는 저장소에 넣지 않는다.
- **공개 저장소 확인:** 커밋 전에 실제 거래 관련 이름이 저장소에 없는지 로컬에서 검색한다. 검색어 목록은 저장소에 두지 않는다.

## 10. 후속 과제

- **상환스케줄 자동 생성:** `schedule:`(발행일, 만기, 거치기간, 상환 주기와 금액, 만기 일시상환)으로 별첨 표를 만든다. 먼저 정할 것은 세 가지다. 휴일 캘린더를 외부 패키지와 직접 관리 목록 중 무엇으로 할지, 영업일 조정 규칙, 합계 검증 방식이다.
- **Word 안 자동 연동:** 같은 키의 콘텐츠 컨트롤을 문서 내부 XML에 바인딩해, 한 곳을 고치면 나머지가 함께 바뀌게 한다. 이번 태그를 그대로 재사용한다. 한컴오피스와 변경 추적에서의 동작을 먼저 확인한다.
- **구조도 전용 도식**, **DRAFT 워터마크(로드맵 E8)**, **컴플라이언스 표시(로드맵 D3)**.

## 11. 결정 기록 (2026-09-29)

- **입력 방식:** Markdown 본문과 YAML 조건을 함께 쓴다.
- **우선순위:** 서식 맞추기와 수치 일관성. 상환스케줄 계산과 조항 초안은 후순위다.
- **수치 일관성 방식:** 수정이 원본 재생성과 Word 편집에 섞여 일어나므로 조건 변수와 불일치 검사(A)를 택했다. Word 안 자동 연동(B)은 후속이다.
- **세부 서식:** 소유자 위임에 따라 작성자가 IB 문서 관행으로 정했다. 고정 라벨 폭, 내어쓰기, 모든 쪽 기밀 표시, 쪽 나눔 규칙, 바닥글, 한국어 어절 줄바꿈, `prepared_by` 명칭이 여기에 해당한다.
