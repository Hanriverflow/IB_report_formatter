# 실사용 공문 실패에 따른 개선 및 검증 결과

## 결론

실제 공문 작성 과정에서 드러난 문제를 재현하고 공통 엔진·회귀 테스트·Word 검증 절차에 반영했다. 전체 자동 테스트 **295개**가 통과했다. 기본 공문과 별첨 공문을 포함한 **9개 문서, 총 16페이지**를 실제 Word에서 렌더하여 모두 확인했다. 이 기록은 2026-09-14의 기존 완료 기록을 대체하지 않고 그 이후의 품질 개선을 설명한다.

코드 변경은 작업 트리에 반영했으며 버전 2.0.0의 미배포 후속 개선으로 CHANGELOG의 Unreleased에 기록했다. 커밋·push·외부 배포는 하지 않았다. Word→MD는 폐기 상태를 유지한다.

## 실패 원인과 구현

| 실제 문제 | 원인 | 프로젝트 반영 |
|---|---|---|
| 본문·표에 `<br>`가 문자로 남음 | 문단 끝 처리만 있고 인라인 처리 누락 | 본문·강조·제목·목록·표에서 실제 `w:br` 생성 |
| 코드 안의 `<br>`도 바뀜 | 강조·수식 파서가 코드보다 먼저 처리 | 코드 구간을 먼저 보호한 뒤 원문 복원; 링크 주소·통화·선행 0 보존 |
| 문단 옆 검은 사각형 다수 | 개별 문서 보정 코드의 Normal·본문·표 keepLines 일괄 적용 | 페이지 제어 표시와 글머리표 구별, 진단 경고와 회귀 테스트 추가 |
| 공문 구성에 별도 후처리 필요 | 범용 공문 서식과 별첨 경계 표현 부족 | 공통 렌더러에서 정식 공문 개시·종결·명시적 별첨 구성 |
| 파일 생성·구조 검사를 완료 판정으로 오인 | 실제 페이지 확인 기록과 구분 미흡 | Word 이미지 검증, 해시·쪽수·버전 기록, 별도 육안 검토 상태 |

검은 사각형 문제를 엔진의 Normal 스타일 결함으로 잘못 일반화하지 않았다. 코어의 기본 Normal은 이미 본문 전체를 묶지 않았으며, 제목에 필요한 keep-next/keep-lines는 그대로 유지한다. Word의 편집기호 표시 설정도 변경하지 않는다.

공문은 회사명 → 수신·참조·제목 → 본문 → 붙임 → 끝 → 발신인 → 시행·연락처 순서로 구성한다. 긴 메타데이터는 값 아래에 줄맞춤하고 중복 회사 머리말은 출력하지 않는다. 붙임은 편집 가능한 Word 번호이며 본문 번호와 별도로 시작한다. 이미 있는 본문 끝 표기를 중복하지 않는다.

`letter.appendix_heading`의 정확히 일치하는 유일한 H1 앞에서 공문을 닫고 새 페이지를 시작한다. 선택적인 `appendix_label`을 지원한다. 경계가 없거나 중복되거나 문서 제목과 같거나 앞에 본문이 없으면 저장 전에 거부한다. 설정을 생략한 기존 공문은 전체 MD를 본문으로 취급한다. 별첨 증빙의 실제 존재나 외부 파일 삽입을 자동 추정하지 않는다.

## 자동 검증

환경: Windows, Python 3.12.12, pytest 9.0.2. 매 실행마다 실제 OS 임시 폴더 아래 새로운 절대 basetemp를 사용했다.

| 검사 | 결과 |
|---|---|
| 최초 회귀 재현 | 신규 요구·결함 테스트 29개 중 27개 실패, 2개 통과 후 수정 |
| 마지막 코드 리터럴 경계 재현 | 강조·수식이 섞인 코드 2개 실패 후 수정 |
| 최종 전체 테스트 | **295 passed, 10.82s**; 이전 251개 대비 44개 추가, 기존 테스트 삭제 없음 |
| Ruff | 이번 변경 Python/테스트 8개 파일에서 All checks passed |
| mypy | 핵심 9개 모듈에서 Success: no issues found (`--follow-imports=silent`) |
| 저장 경로 일치 | 동일 MD의 CLI·API·레지스트리 생성 document XML 일치 |
| 엄격 저장 차단 | 잘못된 별첨 경계의 CLI 실패 및 출력 파일 미생성 |
| Word QA 사전 검사 | 비어 있지 않은 출력 폴더 보존·거부, 음수 기대 쪽수 거부; Word 실행 없이 테스트 |

| 실패 경로 확인 | 별첨 공문에 ExpectedPages 1 지정 시 실제 2페이지 기록 후 종료 코드 1 |

핵심 시나리오는 실제 파싱 → 렌더링 → DOCX 저장/재열기로 검증했다. 본문·강조·목록·제목·표의 줄바꿈, 이스케이프·코드블록·인라인 코드, 링크 주소, 선행 0, 기본/별첨 공문, 명시적 표지 옵션, 끝 중복 방지, 메타데이터 줄맞춤, 붙임 번호, 스타일 상속 및 직접 false 재정의를 포함한다.

코드 리터럴의 마지막 수정 후 새로 생성한 9개 예제의 본문·스타일 XML이 시각 검토한 최종 문서와 모두 동일함을 확인했다.

## 실제 Word 페이지 검토

Windows PowerShell 5.1, Word version 16.0 / build 16.0.20326. `documents` 스킬의 렌더 후 페이지 확인 원칙을 적용했다. 번들 Python의 `render_docx.py`는 `LibreOffice soffice.exe was not found on PATH`로 실패했으며, 사용자 설치를 변경하지 않았다. 대신 프로젝트의 `scripts/word_visual_qa.ps1`로 Word의 네이티브 페이지 EMF를 PNG로 출력했다. PDF 생성 성공을 주장하지 않는다.

| 문서 | 페이지 | 확인 내용 |
|---|---:|---|
| office-letter | 1 | 수신·참조·제목 정렬, 가나다 하위 번호, 표, 붙임 1·2, 끝, 발신·시행·연락처 |
| office-letter-appendix | 2 | 본문 1~4와 붙임 1~2 구분, 1쪽 발신·연락처, 2쪽 별첨·두 표, 셀 내 연락처 줄바꿈, 1/2·2/2 |

모든 페이지에서 한글 누락·문단/표 겹침·잘림·의도하지 않은 빈 페이지가 관찰되지 않았다. 가로 구역 전환 예제의 넓은 여백은 페이지 기하 검증용 구성이다. 공문의 인쇄용 페이지 이미지에는 불필요한 검은 사각형이나 문자로 남은 `<br>`가 없다. 편집기호를 켠 Word에서 필요한 제목·메타데이터 문단의 페이지 제어 표시가 보일 수 있으며 이는 글머리표가 아니다.

## 검증 기록의 식별

로컬 증거 루트: `.dryforge/qa/improvement-20260915/` (git 제외). 스크립트가 만든 manifest의 `visualReview`는 자동 판정을 피하기 위해 `pending`으로 유지했다. **육안 확인 완료 판정은 이 절의 대상·해시·관찰 결과에 기록한다.**

| manifest | SHA-256 | 이 기록에서 확인한 범위 |
|---|---|---|
| `pages-v1/manifest.json` | `E09BF5735ED901641B37CD3309BBB9D239E368A1ADB3FB62A6112B1CBC1F71C1` | 전체 16쪽 최초 확인; 공문 두 종류의 최종본은 아래 v2를 사용 |
| `default-pages-v2/manifest.json` | `67EA2B9DA8B21E81E708CCA61C8FB6A80090739C5EAB58F23B89DF5483387802` | 최종 기본 공문 1쪽 |
| `appendix-pages-v2/manifest.json` | `2DB49AD3E1B0F2F9B60CF1A9BD9331D5664ACDDE43F0E85EE605440E38407995` | 최종 별첨 공문 2쪽 |

각 manifest는 원본·갱신 DOCX·PNG 해시, 원본 변경 여부, Word 버전·생성 시각, 실제·기대 쪽수를 포함한다. 모든 해시를 실제 파일과 대조했고 원본 불변 및 구조 오류 0을 확인했다. `expected-mismatch/`는 의도적으로 실패시킨 쪽수 검사 증거이며 합격 산출물로 취급하지 않는다. 출력 폴더 재사용은 거부되므로 다른 실행의 오래된 이미지를 이번 결과로 오인하지 않는다.

## 사용 및 잔여 한계

```powershell
uv run md-to-word samples/qa/office-letter-appendix.md .dryforge/qa/my-letter/docx/letter.docx --strict
powershell.exe -NoProfile -File scripts/word_visual_qa.ps1 -InputDirectory .dryforge/qa/my-letter/docx -OutputDirectory .dryforge/qa/my-letter/pages -ExpectedPages 2
uv run docx-audit .dryforge/qa/my-letter/docx/letter.docx
```

실행할 때마다 새 출력 폴더를 사용한다. 구조 오류 0, 페이지 수 일치, 이미지 생성은 육안 확인을 대체하지 않는다. 쪽수는 입력 분량·글꼴·Word 버전에 따라 달라지므로 모든 신규 문서를 1~2쪽으로 보장하지 않는다.

실제 거래명·은행 계좌·담당자 연락처·사문서는 새 코드/테스트/샘플/배포물에 넣지 않았다. 이번 QA는 가상 예제로만 수행했으며, 앞서 완성한 개인 공문 파일과 참조 HWPX는 다시 수정하지 않았다. 사용자 Word 문서·프린터·전역 표시 설정을 바꾸지 않았다. 한글 경로의 Markdown 이스케이프를 무조건 제거하는 자동 보정도 도입하지 않았다.

회사별 최종 양식 승인, 임의 DOCX/HWPX 양식 자동 복제, 완전한 CommonMark, 회계·법률 적합성, 다른 OS/Word 버전에서의 동일 페이지, 무인 Office 서버/PDF 배포는 보증 범위 밖이다. 이번 개선계획에서 확정한 구현·회귀검증·페이지 확인은 완료했다.
