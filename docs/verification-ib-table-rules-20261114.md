# IB 표 규칙(E6) 검증 (2026-11-14)

이 문서는 로드맵 E6(IB 표 규칙)의 조사 결과와, 그 결과로 더한 두 가지 기능의 검증 기록이다. 두 기능은 모두 **표 사양에 적었을 때만** 동작한다. 그래서 "적은 표에서 무엇이 생기는가"와 함께 "적지 않은 표와 기존 문서가 그대로인가"를 같이 적는다. 구조 검사 통과는 시각 검토 통과를 뜻하지 않으며, 한 검증과 하지 않은 검증을 나누어 적는다.

**소유자 결정(2026-11-14).** 조율 세션을 통해 받은 답이다.

- **D4(음수 표시 기본값):** 기본값은 바꾸지 않는다. 금융 표의 음수는 지금처럼 적은 그대로 빨강으로 표시한다. 대신 표마다 `( )`, `-`, `△`를 고를 수 있게 하고, 고른 표의 음수는 **검정**으로 표시한다.
- **합계선 모양:** 소계는 위 단선과 굵은 글씨, 합계는 위 단선·아래 이중선·굵은 글씨. 선 색은 프로필의 표 선 색. 합계 행이 표의 마지막 행이면 아래 이중선이 표 아래쪽 바깥선을 대신한다(그대로 둔다).
- **그 밖의 후보:** 이번에는 넣지 않는다(추정 열 음영, 파생 % 이탤릭, NM 범례, 소수점 탭 정렬).

**결과.** 저장소 기존 샘플 13개 문서(32쪽)의 Word 쪽 이미지는 변경 전과 **화소 단위로 같다**(Word의 두 가지 그림 경로 모두). 기존 XML 스냅숏은 하나도 바뀌지 않았다. 바뀐 기존 스냅숏은 모델 스냅숏 11개이고, 표마다 빈 기본값 세 줄이 **추가된 것뿐**이다(3절). 새 기능을 쓴 시험 문서 8개와 새 샘플 1개의 모든 쪽(26쪽)을 보았다. Word 스키마 검사는 오류 0건이다.

## 1. 조사에서 확인한 사실

조사는 코드를 바꾸지 않고 했다. 엔진이 만든 DOCX의 **사본**을 고쳐 Word로 열고, 가상 회사·가상 숫자로 만든 시험 문서로 비교했다.

**지금 코드가 하는 일(변경 전).**

- 표 사양에 쓸 수 있는 키는 13개였고, 모르는 키나 잘못된 값은 strict 모드와 일반 모드 **모두**에서 변환을 거부한다. 그래서 새 키를 더해도 지금 변환되는 문서에는 영향이 없다.
- 표 종류를 머리행 낱말로 추측하는 것은 IB 프로필 두 개(ib-report, ib-memo)뿐이다. 일반 프로필 네 개와 텀싯은 추측하지 않는다. 다만 사양에 `type: financial`이나 `type: sensitivity`를 **적으면** 일반 프로필에서도 그대로 적용한다(기존 테스트가 고정해 둔 동작). 금지된 것은 추측이고, 명시한 사양은 모든 프로필에서 쓰인다.
- **합계 행을 추측해 꾸미는 곳은 없었다.** 텀싯 표에서 `합 계 | << | <<`처럼 첫 열에서 시작한 병합 칸이 라벨 음영을 받을 뿐이다.
- 음수: `(…)`, `-…`로 적은 값만 음수로 읽는다. 빨강은 금융 표에서만 쓰고, text·code·date 열에는 쓰지 않는다. 표기는 원문 그대로 두고 천 단위 쉼표만 더한다. `△1200`처럼 적은 값은 음수로 읽지 않아 쉼표도 빨강도 붙지 않는다.
- 표 테두리는 표 전체에 한 벌뿐이었다. 칸 단위 테두리는 없었다.
- 저장소 샘플의 표 21개 가운데 합계 행은 텀싯 상환표 2개에만 있었다. 음수는 IB 샘플 두 개에 9칸 있었고 모두 괄호로 적혀 있다.

**로드맵의 서술과 다른 점.**

1. 로드맵이 새로 넣을 항목으로 적은 "단위 캡션 `(단위: 백만원)`"은 **이미 있었다**. 표 사양의 `unit`을 적으면 표 위에 `단위: …` 줄이 생긴다.
2. "NM 같은 표시를 원문 그대로 오른쪽 정렬"도 열 역할이 숫자인 표에서는 **이미 그렇게 나온다**. 새로 할 수 있었던 것은 NM 범례 자동 삽입뿐이다.
3. "일반 프로필에는 적용하지 않는다"는 서술과 달리, 일반 프로필도 명시한 표 의미는 지금 적용한다. 새 키를 일반 프로필에서 무시하면 이 선례와 어긋나고, 작성자가 적은 것이 말없이 사라진다. 그래서 새 키는 프로필 7종 모두에서 동작하게 했다.
4. "출력이 바이트 단위로 같다"는 DOCX 파일이 아니라 **XML 스냅숏과 쪽 이미지가 같다**로 확인했다. DOCX 파일은 저장 시각 등으로 바이트가 달라질 수 있다.
5. `△`로 적은 음수가 음수로 읽히지 않는다는 점은 로드맵에 없었다.

**Word 실험(코드 변경 전).** 합계·소계 선과 굵은 글씨는 지정한 행에만 생겼고, 머리행 2줄·병합 칸·쪽 넘김에서도 맞았다. 음수 세 방식 모두 정상이었다. 괄호 음수는 오른쪽 정렬에서 `)` 한 글자만큼 양수보다 왼쪽에 놓인다. 이것은 지금 문서도 같다. 소수점 탭을 쓰면 끝자리가 맞지만, Word에서 사람이 열 너비를 바꾼 뒤의 동작은 확인하지 않아 넣지 않았다. 파생 % 이탤릭은 숫자에서 눈에 잘 띄지 않았고, 추정 열 음영은 IB 줄무늬를 덮었다. 세 가지는 소유자 결정에 따라 넣지 않았다.

## 2. 더한 것과 이유

### 2-1. 합계·소계 행 (`ca798d1`)

```yaml
tables:
  - type: financial
    header_rows: 2
    subtotal_rows: [3, 5]   # 매출총이익, 영업이익
    total_rows: [8]         # 당기순이익
```

- 숫자는 **첫 본문 행을 1로 세는 행 번호**다. 머리행은 세지 않는다. `header_rows: 2`이면 Markdown 셋째 행이 1이다. 민감도 표의 `base_case`와 같은 규칙이다.
- 소계 행: 행 위에 0.75pt 단선, 그 행의 모든 글자 굵게. 합계 행: 여기에 행 아래 0.5pt 이중선이 더해진다.
- 선 색은 프로필의 표 강조색이다(IB 남색 `003366`, 일반 프로필 짙은 회색 `202020`, 텀싯 남색 `1A2270`).
- 위 단선은 그 행 칸의 위 테두리와 바로 위 행 칸의 아래 테두리에 함께 넣는다. Word는 맞닿은 두 칸의 선 가운데 하나를 골라 그리므로, 한쪽에만 넣으면 옅은 격자선이 이길 수 있다.
- 줄무늬·라벨 음영, Markdown으로 쓴 굵게, 음수 빨강은 그대로다. 글자와 숫자는 바뀌지 않는다.
- `합계`라고 적힌 행이라도 목록에 없으면 아무것도 하지 않는다. 상환표 검사용 `schedule.total: true`도 모양을 바꾸지 않는다.
- **세로 병합 칸이 지나가는 행**(조사에서 실험하지 않았던 경우): 이번에 Word로 확인했다. 목록에 든 행의 칸 가운데 위에서 내려온 병합 칸(`^^`)도 다른 칸처럼 선을 받지만, Word는 병합된 칸 안쪽에 선을 그리지 않는다. 그래서 선은 병합 칸 앞에서 멈추고, 병합 칸은 한 칸으로 남는다. 합계 행의 첫 칸이 아래 행으로 이어지는 병합의 시작 칸이면, 이중선은 병합되지 않은 칸 아래에만 그려진다. 이 모습이 표의 뜻과 맞아 거부하지 않고 허용했다. XML 쪽은 테스트로 고정했다(`test_a_vertically_merged_cell_crossing_a_named_row_keeps_its_merge`).
- 거부하는 입력(strict·일반 모드 모두): 목록이 아닌 값, 정수가 아닌 값(`"3"`, `true`, `2.0`), 1보다 작거나 본문 행 수보다 큰 번호, 같은 번호를 두 번, 같은 행을 두 목록에 동시에.
- 칸 테두리는 손으로 만드는 XML이므로 규격 순서를 지키도록 `ooxml_order.py`에 `tcBorders` 순서표를 더하고, `TableStyler.set_cell_border`를 통해서만 넣는다.

### 2-2. 표별 음수 표시 (`d667e8f`)

```yaml
tables:
  - type: financial
    negative: paren       # paren (1,234) / minus -1,234 / triangle △1,234
```

- `type: financial`을 **같은 사양에** 적은 표에서만 받는다. 빨강이 지금 금융 표에서만 쓰이는 것과 같은 범위다. 머리행 낱말로 금융 표로 추측된 IB 표라도 사양에 적지 않았으면 거부한다(가장 좁은 해석).
- 바뀌는 칸: 엔진이 숫자로 서식을 입히는 열에서 `(…)`, `-…`로 적은 금액 전체. 그리고 **옵션을 쓴 표에서만** `△…`로 적은 금액도 음수로 읽는다(같은 표 안의 표기를 통일하기 위해서다). 옵션이 없는 표의 `△1200`은 지금처럼 적은 그대로 둔다. 이것도 가장 좁은 해석이다.
- 숫자와 단위는 바꾸지 않는다. 쉼표만 더한다. 단위가 붙은 값을 괄호로 바꾸면 단위는 괄호 안으로 들어간다: `-3.5%` → `(3.5%)`, `(1200)억원` → `(1,200억원)`.
- 옵션을 쓴 표에서는 엔진의 자동 빨강을 끈다. 그래서 평범한 음수는 검정이다. 문서에 직접 지정한 색과 링크 색은 그대로다(8절의 [2]). 옵션이 없는 표는 그대로 빨강이다. 옵션이 없는 표에서는 자동 빨강이 직접 지정한 색도 덮는다(기존 동작, 바꾸지 않음; 8절 2차 검토의 [6]).
- 건드리지 않는 것: text·code·date 열, 증감 화살표 `▲`·`▼`, `NM`·`N/A` 같은 표시, 양수, 머리행. 부호와 숫자의 서식이 달라 한 금액이 여러 조각으로 나뉘어 적힌 칸(예: `-**1200**`)은 표기를 바꾸지 않고 옵션 없는 표처럼 `-1,200`으로 두며, 자동 빨강은 끈다. 처음 구현(`d667e8f`)은 이 설명과 달리 조각마다 바꿔 금액을 깨뜨렸고, `43f75ea`에서 칸 전체를 한 번 읽도록 고치고 경고를 남기게 했다(8절).
- 거부하는 입력: `paren`, `minus`, `triangle` 이외의 값(대소문자 구분), 그리고 `type: financial`이 같은 사양에 없는 `negative`.

## 3. 바뀐 스냅숏

|---|---|---|---|

모델 스냅숏은 문서 모델의 모든 필드를 적어 두는 검사다(`tests/snapshot_helpers.py`). 새 필드 세 개를 `Table`에 넣었으므로, 표가 있는 샘플 11개의 모델 스냅숏에 빈 기본값 줄이 생기는 것은 피할 수 없다. 조율 세션이 이 방식(필드 추가와 해당 줄만 갱신)을 승인했다. 스냅숏 도우미는 고치지 않았다. **XML 스냅숏 변경 0건은 기존 샘플의 Word 출력이 그대로라는 뜻이다.** 새 필드는 `Table`의 마지막 필드인 `schedule` 앞에 두었다. 맨 끝에 두면 기존 마지막 줄 `"schedule": null`에 쉼표가 붙어 그 줄이 바뀌기 때문이다. 그래서 기존 줄은 하나도 바뀌지 않고 줄만 더해졌다.

## 4. 완료 기준 확인

로드맵 4번의 완료 기준: **명시한 행에만 합계선과 굵게가 적용되고, 사양이 없는 표와 일반 프로필 표의 산출물은 이전과 같다.**

| 기준 | 확인 | 결과 |
|---|---|---|
| 명시한 행에만 선·굵게 | 프로필 7종 각각에서 행마다 위·아래 테두리와 굵게를 XML로 검사(`test_only_named_rows_are_ruled_and_bold`) | 통과 |
| `합계` 글자로 추측하지 않음 | 목록 없는 표의 `합계` 행에 테두리·굵게가 없음(7종) | 통과 |
| 사양 없는 표 그대로 | 같은 문서에서 목록을 적지 않은 표의 XML이 목록 없는 문서와 같고, 빈 목록을 적은 문서 전체 XML이 목록 없는 문서와 같음(7종). 목록을 적은 표에서는 지정 행과 그 바로 위 행만 바뀜 | 통과 |
| 일반 프로필 표 그대로 | 위 테스트의 일반 4종 + 기존 XML 스냅숏 0건 변경 + 기존 샘플 쪽 이미지 화소 동일 | 통과 |
| 머리행 여러 줄·병합 칸 | 머리행 2줄에서 첫 본문 행부터 셈, 병합된 `합 계` 라벨 칸 전체에 선 | 통과 |
| 음수 옵션 | 세 방식 × 3개 프로필에서 음수 칸만 바뀌고 숫자는 같음, 빨강 없음, text 열의 ▲▼△와 `NM`·양수 그대로, 옵션 없는 표 그대로 | 통과 |

**쪽 이미지 도구의 표시 문제(이번에 고치지 않음).** 저장소의 `scripts/word_visual_qa.ps1`은 Word가 그린 쪽 그림(EMF)을 비트맵으로 바꿔 저장한다. 이 기기에서는 이 그림이 **음영 없는 칸의 글자를 음영 있는 칸보다 굵게** 그린다. XML에는 굵게가 없다(두 칸 모두 `<w:b w:val="0"/>`). 굵게와 선을 판정해야 하는 이번 작업에서는 이 그림으로 판정할 수 없었다.

- 재현: IB 프로필(줄무늬 음영이 있는) 표가 있는 문서를 이 스크립트로 그리면, 음영 없는 행의 본문 글자가 굵게 보인다. 같은 문서를 Word에서 PDF로 저장해 그리면 그렇지 않다.
- 그래서 굵게와 선의 판정은 **Word가 직접 저장한 PDF**(`SaveAs2`, 형식 17)를 Windows 내장 PDF 렌더러(`Windows.Data.Pdf`)로 그린 이미지로 했다. 내려받은 프로그램은 없다. 쪽수는 저장소 스크립트의 매니페스트로 판정했고, 두 경로의 쪽수는 모든 문서에서 같았다. 기존 샘플의 변경 전후 화소 비교는 두 경로 모두에서 했다.
- Word의 숨김 모드에서 `ExportAsFixedFormat`으로 PDF를 만들 때 한 번 응답이 멈춘 적이 있어 `SaveAs2`를 썼다. 멈춘 것은 이 작업이 띄운 Word 하나였고, 그 프로세스만 끝냈다.

**정한 규칙.**

- 앞자리 0: 옵션 경로는 숫자 글자를 하나도 버리지 않는다. 정수부가 0으로 시작하는 금액(`(0001.20%)`, `(0001200억원)`, `−0001200`, `-01,200`; 코드일 수 있다)은 옵션 표에서도 바꾸지 않아, 옵션 없는 표와 칸 글자가 같다. 옵션 없는 표의 기존 동작은 바꾸지 않았다: 그 경로는 `(0001.20%)`, `(0001200억원)`, `−0001200`, `-01,200`은 적은 그대로 두지만, `-0001200`과 `(0001.20)%`는 `-1,200`, `(1.20)%`로 앞자리 0을 지운다(기준 `84cde43`부터의 동작). 옵션 표는 이 경우에도 옵션 없는 표와 같은 글자를 낸다.
- 전각 숫자: 금액 패턴이 받는 숫자(전각 포함 유니코드 십진 숫자)를 0 판정에도 그대로 쓴다. 옵션 없는 표가 `-１２３４`를 `-1,234`(ASCII)로 쓰므로 옵션 표도 같은 방식으로 읽고 써서 `paren`이면 `(1,234)`가 된다. 전각 0(`-０`)과 전각 앞자리 0(`-０１２３`)은 옵션 없는 표와 같은 글자다.
